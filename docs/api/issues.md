# API·DTO 초안에서 정할 것

초안을 쓰며 명세·테이블만으로 정하지 못한 것이다. 정하면 해당 도메인 파일을 고치고 여기서 지운다.

## API

초안을 쓰면서 명세만으로 정할 수 없었던 것이다. 묶음별로 적었고, 같은 문제가 두 묶음에 나올 수 있다. 통합 때 정한 것은 3.0에 있다.

### 3.0 통합 때 정한 것

- 로그아웃은 `POST /auth/logout` 하나로 했다(공통레이아웃 묶음의 `POST /members/me/logout`을 뺐다). 토큰 재발급 `POST /auth/refresh`와 같은 곳에 둔다.
- 마이페이지의 현재 비밀번호 확인·변경(MYP-040-01·06)을 맡는 API가 어느 묶음에도 없어 `POST /members/me/password-verification`, `PATCH /members/me/password`를 AIC 담당(2026-10-19부터 YAY)으로 넣었다(기능 분배 3.1절 4번).
- 털색 등 공통코드 목록(MYP-003-03)을 맡는 API가 없어 `GET /common-codes`를 LJS 담당(`global/code`)으로 넣었다. 쿼리 이름 `prntComCd`는 가정이다.
- 메인 위젯 순서(`/members/me/dashboard-widgets`)를 `member` 아래에 두었지만, 저장 위치는 기능 분배 문서 9장에서 미정이다.
- 영수증(`/receipts`)의 도메인은 `expense?`로 두었다. 저장 위치(`expense` 또는 AI 서버)가 미정이다.

### 공통레이아웃·메인

1. **메인 조회 조합 API를 두지 않음** — `milestone.md` 담당 표 YAY 담당에 "메인 조회 조합"이 있지만 MAN 명세 어디에도 "한 번에 불러온다"는 서술이 없다. 초안 작성 규칙 4에 따라 새 API를 만들지 않고 기존 API(반려동물 목록·프로필, 캐릭터 이미지, 건강 지표 요약, 메인 케어리스트, 위젯 설정)를 여러 번 부르는 것으로 두었다. 조합 API를 둘지 결정 필요. 근거: MAN-001·003~006·009.
2. **위젯 순서 저장 단위 모순** — MAN-007은 "반려동물 단위로 저장"인데 MBR_DSHBD_WDGT는 MBR_SN만 있고 PET_SN이 없다(회원 단위). MAN-004도 탭 전환 시 위젯이 개체 기준으로 바뀐다고 한다. 테이블에 PET_SN을 추가할지, 회원 단위로 명세를 고칠지. 근거: MAN-004·007.
3. **위젯 조정 방식·숨김 1종 선택 주체 불명** — MAN-007 본문에 조정 방식(드래그 등) 없이 저장 결과만 있다. MAN-006 "6종 중 최대 5종 노출, 1종 숨김"에서 숨길 1종을 회원이 고르는지 고정인지 없다(INDCT_YN 컬럼은 있음). PUT 요청에서 표시 5종 초과를 400으로 막을지 결정 필요. 근거: MAN-006·007.
4. **"AI 건강분석 리포트" 위젯 정의 없음** — 데이터 출처·담당이 없다(기능 분배 3.1절 14번 남은 일과 같음). 근거: MAN-006.
5. **MBR_DSHBD_WDGT 패키지 위치** — MBR_ 접두 테이블이라 도메인을 member(0층)로 두었으나 구현은 YAY다. member 패키지에 YAY가 만들지, 별도 패키지로 둘지. 근거: MAN-006·007.
6. **비로그인 메인 접근 모순** — MAN-001은 "비로그인이면 기본 캐릭터"라 하지만 COM-002-02는 레이아웃을 쓰는 모든 페이지가 로그인 필수, COM-003-08은 로그인 상태만 메인으로 보낸다. 메인이 비로그인 공개면 쓰는 API(반려동물·캐릭터)의 인증 예외가 필요하다. 근거: MAN-001, COM-002-02, COM-003-08.
7. **알림 수신 설정 저장 위치와 경로** — 설정 값이 MBR 컬럼(member 0층)에 있는데 API 담당은 notification(LJS)이다. notification → member 호출은 층 규칙상 가능하나 MBR 컬럼 수정 service를 어느 도메인에 둘지 정해야 한다. 경로는 `/members/me/notification-settings`로 임시 지정. 근거: COM-008-02·14·20.
8. **캐릭터 생성 알림 수신 설정 모순** — COM-008-12는 "항상 받는 알림에 잠정 배치, 설정 가능 여부 확정 필요"인데 MBR.CHAR_CRT_NOTI_RCPTN_YN 컬럼이 이미 있다. 설정 응답·요청에서는 뺐다. 근거: COM-008-12.
9. **수신 설정 기본값 적용 위치** — 가입(ACC, YAY)이 행을 만들 때 넣는지 DB 기본값인지 없다. "케어 일정 ON(D-1)"을 d1BfhdNotiYn=Y, 나머지 시점 N으로 해석했다. 근거: COM-008-13.
10. **사전 알림 시점 검증 규칙 없음** — 케어 일정 ON인데 시점을 하나도 고르지 않은 경우, 케어 일정 OFF일 때 시점 값 처리(저장 유지/무시)가 없다. 근거: COM-008-05·06.
11. **한도 미설정 판정의 소관** — COM-008-10 안내를 위해 설정 응답에 `expndLimSetYn`(MBR.MM_EXPND_LIM_AMT 존재 여부)을 넣었다. 한도는 expense(SJM, 3층) 기능인데 notification(2층)은 expense를 부를 수 없으므로 MBR 컬럼을 member를 통해 읽는 것으로 가정했다. 확인 필요. 근거: COM-008-10, 기능 분배 3.1절 17번.
12. **7일 경과 숨김의 판정 방식** — 최신순 정렬(COM-004-05)과 "수신 후 7일" 판정(COM-004-12)은 서버가 INAPP_NOTI.REG_DT(수신 시각)로 한다. 화면에 수신 시각을 표시한다는 명세는 없어 목록 필드에는 넣지 않았다. 숨김을 조회 때 REG_DT + SYS_STNG.NOTI_HIDE_CRTR_DAY_CNT로 계산할지, 알림을 만들 때 AUTO_HIDE_DT를 채워 그 값으로 거를지 정해야 한다. 근거: COM-004-05·12.
13. **7일 경과 알림의 보관·삭제 기준 미정** — "별도 정의"라고만 되어 있고 정의가 없다. 삭제가 필요하면 BATCH 항목이 생긴다. 근거: COM-004-12.
14. **공동양육 초대 알림의 대상 식별자 없음** — 행 안 [수락]·[거절](pet, SJM API)을 부르려면 jntBrupInvtnSn이 필요한데 INAPP_NOTI에는 MVMN_PATH 외 참조 컬럼이 없다. 처리 후 "결과 문구로 전환"을 알림 행에 저장할지(재조회 시 유지)도 없다. 근거: COM-004-08.
15. **펫돌봄 거래 알림의 채팅방 식별자 없음** — 알림 선택 시 해당 채팅방을 열어야 하나 INAPP_NOTI에 otoChatRoomSn이 없다. MVMN_PATH 문자열을 프론트가 해석할지, 컬럼을 추가할지. 근거: COM-004-09.
16. **거래 상태 알림 억제 판정 수단 없음** — 서버가 "회원이 지금 그 채팅방을 모달로 보고 있는지" 알아야 하는데 접속·열람 상태를 저장하는 명세·테이블이 없다(WebSocket 세션 등). 근거: COM-004-14, COM-009-18.
17. **알림 탭 → 유형 묶음의 위치** — 탭(전체·케어·커뮤니티·안내)을 서버가 탭 코드로 받을지, 프론트가 notiTypeCd 목록을 보낼지 정해야 한다. AIMG02 코드값 목록이 입력에 없다. 임시로 `notiTypeCd` 복수 쿼리로 두었다. 근거: COM-004-03·04.
18. **미읽음 수 API 모양** — `/notifications/unread-count`가 규칙 2의 "자원 이름"에 맞는지, 목록 응답에 넣을지 결정 필요. 미읽음 수에 7일 지나 숨긴 알림을 포함할지도 없다. 또 목록은 미리보기 5건만이고 전체 페이지가 없어(COM-004-16) Page 응답의 hasNext가 쓰이지 않는다. 근거: COM-002-09, COM-004-02·05·12·16.
19. **로그아웃 경로·토큰 전달·폐기 방식** — 경로 `POST /members/me/logout`은 임시이며 ACC 그룹 로그인 경로와 맞춰야 한다. Refresh 토큰 전달 방식(쿠키·본문)이 없다. 기능 분배 3.1절 28번은 "Refresh 토큰 삭제"인데 RFRSH_TKN에는 DSCD_DT(폐기일시)가 있어 행 삭제인지 폐기 표시인지 갈린다. 근거: COM-005-07·08, 기능 분배 3.1절 28번. **[2026-10-22 결정]** 경로는 `POST /auth/logout`, 토큰은 쿠키(로그인 쪽 6번), 폐기는 `LoginSessionManager.revoke`(RFRSH_TKN 행 폐기)
20. **회원 요약 조회의 범위·이미지 제공 방식** — (a) 프로필 사진을 MBR.ATCH_FILE_SN만 줄지 URL로 줄지(보호 파일 다운로드 경로 여부) 없다. (b) CMU-005-02는 타인(채팅 상대) 요약이 필요할 수 있어 `me` 경로만으로 부족할 수 있다(기능 분배 3.1절 1번 "판정이 갈림"). (c) 이메일 마스킹 규칙이 없고, COM-008-03은 마스킹 없이 표시하는지도 불명. `GET /members/me`(회원정보, SJM)와 겹치는지도 정해야 한다. 근거: COM-002-15, COM-005-02, COM-008-03.

### AI매니저·건강기록

1. **검진기록 테이블에 반려동물·검진일 컬럼이 없음.** `CKUP_RCD`에는 `PET_SN`도, 검진일 컬럼도 없다. 그래서 둘 다 `SCHDL_SN` → `SCHDL.PET_SN`·`SCHDL_DT`로 거슬러 올라가야 알 수 있다. 하위 테이블 `PRSC`·`INSP_NVL`·`ETC_INSP`·`CKUP_RCD_ATCH`도 반려동물 컬럼이 없다. 이 상태에서 연결 일정이 삭제되면 검진기록의 반려동물과 날짜를 무엇으로 정하는지(일정은 `DEL_YN` 소프트 삭제라 남는지), `PetAuthorizer`가 무엇으로 검사하는지 정해야 한다. 컬럼을 추가할지도 함께 정한다. 근거: HLT-002-05·27, HLT-003-33, HLT-011-07, AIM-009-09
2. **검진 하위 자원의 경로 모양.** 초안은 처방·검사 수치·기타검사·반복 예방·첨부를 `/pets/{petSn}/prescriptions?ckupRcdSn=`처럼 반려동물 바로 아래에 두고 쿼리로 걸렀다. 종합 건강기록이 검진을 가로질러 조회하기 때문이다. 다른 안은 `/pets/{petSn}/checkups/{ckupRcdSn}/prescriptions`처럼 중첩하는 것이다. 이 안은 규약의 "한 단계까지 중첩"을 넘는지 판단이 필요하다. 관찰 회차(`observation-cycles`)와 케어 완료(`care-completions`)도 같은 문제다. 근거: HLT-005-02·03·05, HLT-011-08·09, HLT-002-17
3. **영수증의 도메인과 층 규칙.** 영수증 결과 저장은 `health`(검진·일정·처방)와 `expense`(지출, 기능 분배 3.1절 16번)를 함께 쓴다. 그런데 2층 `health`는 3층 `expense`를 부를 수 없다. 따라서 영수증은 `expense` 이상에 둬야 한다. 그렇게 두면 이번에는 검진기록 직접 입력 API(`health`)가 영수증 상태(저장완료)와 연결을 바꿀 수 없다. 초안은 "인식 실패 뒤 직접 입력"을 `POST /receipts/{recptSn}/checkups`로 보냈다. 이렇게 하면 HLT-002 등록 모달이 진입 경로에 따라 서로 다른 API를 부르게 된다. 영수증 도메인과 이 분기를 확정해야 한다. 근거: AIM-010-06, HLT-002-31·41·45, AIM-009-10·24 **[2026-10-22 결정]** 영수증은 `expense` 도메인(3층)에 구현했다. `health` 쪽 저장은 `health` service를 부른다(연결 전에는 가짜, `docs/api/receipt.md`)
4. **OCR 결과를 서버와 화면 중 어디서 가공하는가.** 약품 일수·용법을 복용일·횟수로 바꾸기, 반려동물 구역 나누기, 하단 할인 비율 배분, 검진 내용 자동 채움을 누가 하는지 명세에 주체가 없다. 초안은 `POST /receipts`의 응답에서 가공해 준다고 보았다. `ReceiptResponse.sections`의 모양도 정의가 없다. `RECPT.OCR_RSPNS_JSON`에는 원문만 둔다고 가정했다. 근거: AIM-009-04·16·20·21, HLT-002-40·42
5. **OCR 호출 방식과 멱등 처리.** 초안은 15초 제한 안에서 `POST /receipts`가 동기로 결과를 돌려준다고 보았다. 비동기(상태 폴링)로 할지 정해야 한다. 그 밖에 정할 것이 셋 있다. (1) [취소]를 누른 뒤 서버에서 진행 중인 OCR을 어떻게 처리하는가. (2) [다시 분석]은 같은 `recptSn`을 다시 쓰는가, 새로 업로드하는가. (3) 업로드 단계의 "중복 요청 차단"에 쓸 키는 무엇인가. `IDMPT_DMND_ID`는 컬럼이 하나뿐인데 저장 단계(AIM-009-24)에서 쓰므로 업로드 단계에는 쓸 수 없다. 근거: AIM-008-06·07, AIM-009-24
6. **PDF 분석의 엔진·담당·저장 위치가 없음.** 검사결과지 PDF 분석을 무엇으로 하는지(OCR인지 AI 서버인지) 명세에 없다. 담당(JAJ인지, OCR 공통부 LJS인지)도 없다. 분석 결과를 담을 테이블도 없다. 초안은 `POST /pets/{petSn}/checkup-attachments/{ckupRcdAtchSn}/analyses`가 결과만 돌려주고 저장하지 않는 것으로 두었다. 근거: HLT-005-04, HLT-007-04·06
7. **파일 업로드·보호 파일 조회 방식.** 초안은 관찰 사진과 검진 첨부를 각 자원 API에 multipart로 올리고, 자원별 GET으로 파일 자체를 받게 했다. 공통 파일 API(`global`)를 둘지 정해야 한다. 또 명세 스스로 "확인 필요"로 남긴 것이 있다. `ATCH_FILE`을 언제 소프트 삭제하는가(검진 첨부·영수증 참조가 모두 없어질 때). 근거: HLT-002-22, HLT-005-01, HLT-011-09, AIM-008-09
8. **여러 반려동물을 한 캘린더에 보일 때의 호출 수.** 초안의 `/pets/{petSn}/care-schedules`는 반려동물 하나 단위다. 그래서 통합 캘린더와 다가오는 일정 3건을 보이려면 고른 반려동물 수만큼 호출하고 화면에서 합쳐야 한다. 다른 안은 `GET /care-schedules?petSn=1&petSn=2`(로그인 회원이 연동된 반려동물인지 검사)다. 이 안은 `PetAuthorizer` 규칙의 예외가 된다. 근거: HLT-003-29·39·40
9. **검진기록·일정을 다른 반려동물로 옮기는 API 모양.** 초안은 PATCH 본문의 `petSn`으로 대상 반려동물을 받는다. 이때 정할 것이 셋 있다. (1) 경로의 `petSn`(원래)과 본문의 `petSn`(대상) 둘 다 권한을 검사해야 한다. (2) 함께 옮기는 범위(케어 항목·완료 기록·반복 예방 관리)를 한 트랜잭션으로 묶어야 한다. (3) 공동양육자도 옮길 수 있는지 정해야 한다. 근거: HLT-002-26, HLT-003-37, HLT-005-01
10. **일정 출처 코드(HLTG22)의 값 목록이 없음.** 명세에 나오는 값은 'AI 생성'뿐이다. 검진기록이나 영수증 저장이 자동으로 만든 병원 일정에 넣을 값이 정의되지 않았다. 또 출처를 요청 본문으로 받으면 클라이언트가 값을 꾸며 보낼 수 있다. 서버가 호출 경로로 정할지 결정해야 한다. 근거: AIM-012-13, AIM-009-09, HLT-002-26
11. **기본 케어 항목(11개)과 기본 메인 표시(3개)를 언제 누가 만드는가.** 반려동물 등록은 1층 `pet`이 하므로 2층 `health`의 케어 항목을 만들 수 없다. 방법은 셋 중 하나다. 이벤트로 만들기, 처음 조회할 때 만들기, 항목 마스터를 따로 두기. 근거: HLT-003-12·13
12. **종합 건강기록·메인 대시보드에 조합 조회를 둘지.** 명세에 "한 번에 불러온다"는 서술이 없어 조합 API를 만들지 않았다. 대신 기존 자원 API를 7~8번 부른다. 기능 분배 3.1절 14번 "건강 지표 요약"이 무엇을 담는지는 정의가 없다(기능 분배 3.1절의 남은 일과 같음). MAN-005·006이 무엇을 요구하는지는 이 그룹의 입력에 없다. 근거: HLT-011-02·06·07, HLT-002-09~13
13. **체중 동기화 서술이 서로 맞지 않음.** HLT-011-02는 "일상기록의 최신 체중, 없으면 프로필 체중"이라고 하여 읽을 때 고르는 방식으로 쓴다. 기능 분배 3.1절 23번은 일상기록 체중을 프로필(`PET.PET_BDWG`)에 써 넣는 방식이다. 둘 중 하나로 정해야 한다. 근거: HLT-011-02, HLT-002-11·13
14. **AI 서버가 Spring을 부르는 경로와 인증.** 반려동물을 서버 규칙으로 정하려면(AIM-012-04) 반려동물 목록이 필요하다. 같은 이름 케어 항목 확인(AIM-012-08)과 [등록]도 Spring을 불러야 한다. 이것을 AI 서버가 회원 토큰을 전달해 부르는지, 화면이 직접 부르는지 명세에 없다. 초안은 [등록]을 화면이 직접 부른다고 가정했다. 근거: AIM-012-04·08·09
15. **검사 수치의 중복 기준과 복구 규칙.** "이미 등록된 항목은 제외"(HLT-007-03)와 "삭제한 항목을 다시 추가하면 복구"(HLT-005-02)는 모두 같은 검진기록 안의 같은 항목을 기준으로 한다. 직접입력 항목(`INSP_ARTCL_DRCT_INPT_NM`)도 이름으로 같은 항목인지 판정하는지 정해야 한다. 여러 행을 선택 삭제하는 방식(초안은 `DELETE ?inspNvlSn=`를 반복)도 확정해야 한다. 근거: HLT-005-02, HLT-007-03·04
16. **복용 종료일이 지나면 자동 종료하는 처리의 실행 주체가 없음.** 종료일이 지나면 처방 상태를 '종료'로 바꾸고 투약 케어 항목을 지워야 한다. 이것은 배치 작업이 필요한데 담당과 실행 시각이 정해지지 않았다. 근거: HLT-005-03, HLT-003-12
17. **병원명 최대 길이가 명세와 DDL에서 다름.** 명세는 병원명을 50자로 제한한다고 쓴다. 그런데 `SCHDL.HSPTL_NM`·`CKUP_RCD.HSPTL_NM`은 `varchar(80)`이다. 근거: AIM-009-26, HLT-002-45
18. **케어미션(기능 분배 3.1절 22번)을 부르는 시점이 명세에 없음.** 기록 추가, 케어 완료, 검진 저장 중 어느 동작이 케어미션 진행에 들어가는지 HLT 명세에 서술이 없다. 근거: HLT-003-12, HLT-002-11·25·31·45, AIM-009-09
19. **인식 실패율을 어떻게 모으는가.** `RECPT_STTS_HSTRY`로 집계하는지, 조회 화면(관리자)이 있는지 정의가 없다. 근거: AIM-010-08
20. **메인 표시 저장 경로의 이름.** 화면 이름(`main`)을 경로에 쓰지 않으려고 `PUT /pets/{petSn}/care-item-exposures`라고 지었다. 근거는 `MAIN_EXPSR_YN`(노출)이다. ★ 토글(HLT-003-13)과 메인페이지 순서 변경(MAN-009)이 같은 전체 저장 API를 쓴다는 데 YAY·JAJ가 합의해야 한다. 최대 6개를 넘으면 어떤 오류 코드를 낼지도 정해야 한다. 근거: HLT-003-13

### 마이페이지

1. **"최근 등록 동물"의 기준과 판정 위치가 없다.** 가계부 직접 입력은 여러 마리면 "최근 등록 동물"을 기본 선택한다(MYP-031-02). 대상은 주양육·공동양육 동물 전체다. 공동양육 동물의 "등록"이 반려동물 등록일시(`PET.REG_DT`)인지, 내가 연동된 일시(`BRUP_REL.REG_DT`)인지 명세에 없다. 또 기본 선택은 화면이 하므로, `GET /pets`가 이 순서로 정렬해 줄지 `PetSummary`에 일시 필드를 둘지 정해야 한다. 이 초안은 필드를 넣지 않았다. 대표 승계(MYP-010-05)는 주양육 동물만 대상이라 서버가 `PET.REG_DT`로 판정한다. 가계부 반려동물별 지출의 등록순(MYP-030-05)도 서버가 정렬하지만, 공동양육 동물이 섞이면 같은 기준을 정해야 한다.
2. **체중 수정 잠금 판정을 pet이 할 수 없다.** 프로필 체중은 건강 일지에 체중 기록이 없을 때만 고칠 수 있고, 기록이 있으면 최근 기록값과 기록일을 보여 준다(MYP-002-04, MYP-003-01). 그런데 `pet`(1층)은 `health`(2층)를 읽지 못한다(`AGENTS.md` 층 규칙). PET 테이블에는 체중 기록 유무나 기록일을 담는 컬럼도 없다. 해결 방법은 둘 중 하나다. 기능 분배 3.1절 23번 동기화가 기록일과 유무까지 PET에 넘기도록 컬럼을 추가하거나, 프론트가 `health` API를 따로 부르게 한다. 그래서 `GET /pets/{petSn}`의 `bdwgEditableYn`·`latestBdwgRcdDt`는 가정으로 넣은 필드다. **[2026-10-26 결정]** 컬럼을 추가하지 않는다. 체중 기록과 기록일시는 `DAILY_HLTH_RCD`(지표 `HLTC0014`, `RCD_DT`)에 이미 있어, 프론트가 `GET /pets/{petSn}/daily-health-records?dailyRcdIdctCd=HLTC0014&size=1`(JAJ)로 받아 체중 칸을 잠그고 최근 기록값·기록일을 보여 준다. 서버는 `PATCH`의 체중을 막지 않는다. `PetResponse`에서 두 필드를 뺐다
3. **반려동물 삭제 연쇄의 순서와 호출 주체가 없다(기능 분배 3.1절 29번).** `DELETE /pets/{petSn}`(SJM)는 여러 가지를 함께 처리해야 한다. 픽셀 캐릭터와 보유 아이템 삭제(LJS 자원), 공동양육 연동 해제와 알림, 대표 승계, 그 동물에게 출제된 당일 미션 삭제(MYP-020-03), 지출 유지(MYP-002-07·08)다. 건강기록·일정을 어떻게 처리할지와 AI 펫 태그를 어디에 저장할지도 정해지지 않았다.
4. **식사량·음수량 정상범위를 입력받는 곳이 없다.** PET에는 `MIN_MEAL_QTY`·`MAX_MEAL_QTY`·`MIN_WATR_QTY`·`MAX_WATR_QTY`가 있지만, 등록/수정 모달(MYP-003-01·04)에는 이 입력란이 없다. 어느 화면에서 받는지 정해야 한다. 이 초안은 이 값들을 요청·응답에 넣지 않았다.
5. **공동양육 초대는 반려동물 단위가 아니다.** 초대 하나가 여러 마리를 묶는다(MYP-005-02, INVTN_TRGT_PET). 그래서 `/pets/{petSn}` 아래에 둘 수 없어 최상위 `/caregiver-invitations`로 두었다. 이렇게 하면 `PetAuthorizer`가 적용되지 않으므로, 대상 동물마다 주양육자인지와 5명 상한을 service에서 검사해야 한다. 이 방식을 승인할지 정해야 한다.
6. **미가입자 초대를 수락하는 경로가 없다.** 미가입자에게는 이메일로 초대장을 보낸다(MYP-005-01). 그런데 수락·거절 경로는 `jntBrupInvtnSn` 기준이고 로그인을 전제한다. `INVTN_TKN_HASH`(초대 토큰)로 조회·수락하는 경로가 필요한지, 가입 뒤 `RCVR_MBR_SN`을 언제 연결하는지 명세에 없다(MYP-005-05·07).
7. **캐릭터 경로에 PetAuthorizer가 적용되지 않는다.** 보유 아이템을 `/pets/{petSn}` 아래에 두면 두 단계 중첩이 되어 `api.md`에 어긋난다. 그래서 `/pixel-characters/{pixelCharSn}` 아래에 두었다. 이 경로들은 `PixelCharacter → petSn`으로 권한을 따로 검사해야 한다(MYP-010-13·16, MYP-011-05·06). 경로 구조를 정해야 한다.
8. **대표 반려동물 지정의 경로 이름과 컬럼 뜻이 불분명하다.** `POST /pets/{petSn}/representative`의 하위 경로 이름은 동사가 아닌 명사로 지었다(MYP-010-05). 또 BRUP_REL에 `RPRS_PET_YN`과 `RPRS_MBR_SN`(대표회원일련번호)이 함께 있는데, `RPRS_MBR_SN`이 무엇을 뜻하는지 명세에 없다.
9. **"공용" 지출을 어떻게 표현할지 정해야 한다.** 공용 지출은 `PET_SN`이 비어 있다. 반려동물 필터에서 "전체"(파라미터 생략)와 "공용"을 구분할 쿼리 값이 필요하고, 중복 확인(MYP-031-06)에서도 공용을 같은 조건으로 거를 값이 필요하다(MYP-030-10, MYP-031-02).
10. **지출의 공유 범위가 명세에 없다.** EXPND에는 `MBR_SN`과 `PET_SN`이 함께 있다. 같은 동물의 지출을 주양육자와 공동양육자가 서로 보는지, 회원별로만 보는지 명세에 없다. 필터에는 "(연동 해제)"·"(삭제된 반려동물)" 표기가 필요하므로, 지출 응답에 반려동물 삭제 여부와 현재 양육관계 유효 여부를 함께 줘야 한다(MYP-030-10, MYP-002-07).
11. **집계 조회 API를 둘지 판단이 필요하다.** `GET /expenses/statistics`·`/totals`·`/months`는 테이블 자원이 아니다. 대안은 프론트가 한 달 치를 모두 받아 직접 집계하는 것이다. 초안 작성 규칙 4는 명세가 한 번에 불러온다고 할 때만 조합 API를 두라고 한다. MYP-030-01의 "화면 전체가 선택한 달 기준으로 갱신"을 그렇게 해석했는지 확인해야 한다(MYP-030-01·02·04~06·09·16·19).
12. **다중 삭제 요청의 모양을 정해야 한다.** "조회 결과 전체 선택"은 화면에 보이지 않는 건도 포함한다(MYP-030-18). 그래서 요청이 `expndSn` 목록이 아니라 범위·필터 조건이 되어야 한다. `api.md` 규약에는 `DELETE` 요청에 본문을 쓰는 예가 없다. `POST /expenses/bulk-delete` 같은 동사 경로가 대안이다(MYP-030-19·21). **[2026-10-22 결정]** 개별 선택은 `DELETE /expenses?expndSn=`(본문 없음), 조건 전체 삭제는 `POST /expenses/bulk-delete`(본문에 범위·필터와 `expectedCnt`). `docs/convention/api.md`에 DELETE 본문 금지를 넣었다
13. **회원정보 수정의 담당이 갈린다.** 기능 분배 3.1절 2·4번은 닉네임·비밀번호의 "검증·변경"을 AIC 담당으로 두었고, `milestone.md` 담당 표은 회원정보 수정을 SJM 담당으로 두었다. 이 초안은 닉네임·비밀번호를 OTHER(AIC, 2026-10-19부터 YAY)로 분류했다. 휴대전화·프로필 사진 저장만 `PATCH /members/me`(SJM)로 두었다. 휴대전화는 기능 분배 3.1절 3번이 정규화·중복 확인만 AIC로 정했기 때문이다(MYP-040-04~06·10·11).
14. **`GET /members/me` 경로가 겹친다.** 기능 분배 3.1절 1번 회원 요약 조회(닉네임·프로필 사진, LJS)와 회원정보 수정 화면 조회(SJM, 이메일·휴대전화·SNS 포함)가 같은 경로가 된다. 두 경로를 나눌지(예: `/members/me/summary`), 하나의 응답으로 합칠지 정해야 한다(MYP-040-02·03·09).
15. **프로필 사진 업로드 API와 해제 규약이 없다.** 파일 업로드 API(ATCH_FILE)를 어느 그룹이 정의하는지 모른다(`global`로 추정). 또 "기본 이미지로"는 `atchFileSn`을 비워야 하는데, `api.md`은 비울 때 빈 문자열(`""`)을 보내라고 한다. 이 필드는 `Long`이라 규약과 맞지 않는다(MYP-040-02·08).
16. **영수증 상태 변경의 호출 방향이 정해지지 않았다.** 직접 입력으로 전환해 저장해도 영수증을 연결하고 영수증 상태를 저장완료로 바꾼다(MYP-031-05). RECPT는 LJS 담당 자원이다. `expense`(3층)가 그 service를 직접 부르는지, RECPT가 어느 도메인 패키지에 속하는지(층 판정) 정해지지 않았다.
17. **캐릭터 생성 완료를 화면이 어떻게 알지 명세에 없다.** 모달을 열어 둔 채 결과 확인(3단계)으로 넘어가는 방식이 정해지지 않았다. `GET /pixel-characters/{pixelCharSn}` 폴링과 알림 중 무엇을 쓸지 정해야 한다(MYP-010-09·10). 사진 첨부 요청의 형식(multipart)과 파일 규칙도 명세에 없다(MYP-010-08).
18. **포인트 월 합계를 누가 계산할지 정해야 한다.** `GET /point-ledgers`는 명세상 페이지가 없는 한 달 전체 목록이다. 그래서 선택한 달의 적립·사용 합계는 프론트가 합산하도록 두었다. 한 달 내역에 건수 상한이 없으므로, 서버가 합계를 줄지 정해야 한다(MYP-020-02).
19. **케어미션 탭 완료 개수를 한 번에 줄지 정해야 한다.** 탭마다 그날의 완료 개수를 표시하므로, 프론트가 반려동물마다 `GET /pets/{petSn}/daily-missions`를 부른다(최대 10회). 날짜를 이동할 때마다 다시 부르게 되는데, 이 방식을 허용할지, 반려동물 전체를 한 번에 주는 조회를 둘지 정해야 한다(MYP-020-03·04).

### 로그인·플레이스·커뮤니티·고객센터

1. **인증 API 경로 이름과 응답 규칙** — `docs/convention/api.md`에 로그인·로그아웃·재발급 경로 예가 없다. 초안은 `/auth/login`·`/auth/logout`·`/auth/refresh`·`/auth/sns-login`·`/auth/captchas`·`/auth/login-attempt-limits`로 두었고, 동사 경로(`login`)가 B규칙 2("동사를 경로에 넣지 않는다")와 부딪힌다. 또 `api.md`은 "상태 변경은 data가 null"인데 `POST /email-certifications/{emlCertSn}/verify`는 분기 결과·권한 토큰을 돌려줘야 한다. 둘 다 예외로 둘지 정해야 한다. 토큰 재발급과 로그아웃은 ACC 명세에 기능 ID가 없다(기능 분배 3.1절 28번 비고). 근거: ACC-002-05·09~11·18, ACC-001-06, ACC-011-08 **[2026-10-20 일부 결정]** 응답 모양은 nct-backend 형식으로 확정(`docs/convention/api.md`). `GET /auth/me`(인증 주체 조회)는 `auth` 도메인에 둔다. 동사 경로(`login`·`refresh`)는 `/auth` 아래에서만 예외로 허용한다
2. **SNS 로그인 흐름** — 백엔드가 OAuth 리다이렉트·콜백을 처리하는지(Spring Security 기본 흐름), 프론트가 인가 코드를 받아 `POST /auth/sns-login`으로 넘기는지 명세에 없다. 신규 가입 확인 상태(제공자·이메일·번호·외부 연령 확인 결과)를 어디에 담아 `POST /members`로 이어 줄지도 정해야 한다. 근거: ACC-002-09~11, ACC-001-31·32 **[2026-10-22 추가]** 흐름에 따라 정할 것: (1) 프론트가 코드를 넘기는 흐름이면 `SnsLoginRequest`에 `state`(CSRF 방지, 네이버 토큰 교환에 필수)·`redirectUri`(인가 요청과 같은 값, 서버 설정에 고정하면 생략)·`codeVerifier`(PKCE를 쓸 때)가 필요하고, 서버가 발급한 `state`인지 확인할 발급 수단(API 또는 쿠키)이 필요하다. Spring 기본 흐름(`/oauth2/authorization/{provider}`)이면 요청 DTO가 없고 성공 핸들러가 `LoginSessionManager.issue`를 부른다. (2) 카카오는 이메일 제공을 거부할 수 있는데 `MBR.ACNT_EML_*`가 NOT NULL이다. 가입을 막을지, 이메일을 직접 입력받아 인증할지 정한다. (3) 비밀번호가 없는 회원(`PSWD_HASH` NULL)이 마지막 SNS 연결을 끊지 못하게 막는다. 기존 계정에 SNS를 연동·해제하는 API는 초안에 없다(MYP-040-09는 조회만). (4) `SNS_ACNT_LINK`는 해제(`USE_YN='N'`) 뒤에도 `UK_SNS_ACNT_LINK_1`이 걸리므로 같은 계정 재연결은 새 행 대신 기존 행을 `Y`로 되살린다
3. **가입 진행 임시 상태를 저장할 테이블이 없다** — 명세는 목적·이메일·약관 버전·확인 번호·요청 식별값·만료시각을 서버 임시 상태로 묶으라고 하지만 DDL에 대응 테이블이 없다(EML_CERT는 인증 한 건만 담는다). 새로고침 복원 API(ACC-001-01)와 같은 가입 시도의 멱등 처리(ACC-001-14·32) 저장소를 정해야 한다(DB 테이블 / Redis 등). 근거: ACC-001-01·14·32
4. **가입 직후 미로그인 상태의 닉네임 설정 권한** — 서비스 로그인 권한 없이 "방금 만든 본인 회원의 닉네임 설정만" 허용해야 한다. 초안은 제한 범위 토큰으로 `PATCH /members/me/nickname`을 부르게 했다. 응답 유실 뒤 저장값을 다시 읽는 경로(제한 토큰으로 회원 요약 조회 기능 분배 3.1절 1번을 허용할지)도 정해야 한다. 근거: ACC-001-22·23·24·26·27·28
5. **공통 인증 설정 값 미확정** — 코드 유효시간, 재전송 간격·횟수·집계 구간, 인증 완료 유지시간, 가입·재설정·복구 권한 유효시간을 "구현 전에 확정"한다고만 되어 있고 SYS_STNG에는 두지 않는다고 적혀 있다. 근거: ACC-001-05, ACC-011-07, ACC-001-43
6. **개인정보가 URL에 실림** — 초안의 `GET /auth/login-attempt-limits?email=`, `GET /members/phone-availability?mblTelno=`는 이메일·휴대전화번호가 쿼리에 들어가 접근 로그에 남는다. 비로그인 사용자가 `/email-certifications/{emlCertSn}`의 일련번호를 그대로 다루면 추측 공격 대상이 된다. POST 본문 전환이나 불투명 토큰 사용을 정해야 한다. 근거: ACC-002-03·22, ACC-001-30, ACC-011-08, ACC-012-06
7. **탈퇴 응답 유실 시 결과 확인 수단** — 명세는 "응답 유실이면 성공 여부부터 조회"하라고 하지만, 탈퇴가 성공하면 모든 로그인 권한이 끝나 `/members/me` 계열로는 조회할 수 없다. 멱등 요청 ID 컬럼도 MBR에 없다. 결과 조회 방식을 정해야 한다. 근거: ACC-020-14·15·16
8. **탈퇴 시 다른 도메인 데이터 처리 미확정** — 게시물·댓글·포인트와 남은 공동양육자의 조회 범위 처리는 명세 스스로 "별도 확정 필요"라고 적었다. 30일 뒤 파기는 기능 분배 3.1절 5번 비고대로 `scheduler`(분배 문서의 `job`) 몫이다. 근거: ACC-020-02·04·14
9. **기능 분배 3.1절 2·4번의 마이페이지 쪽 API를 이 초안에 넣지 않았다** — 기능 분배 3.1절은 닉네임 "검증·변경", 비밀번호 "검증·변경"의 구현 담당을 sannabi1(AIC, 2026-10-19부터 YAY)로 두었는데, 이 그룹 정의는 "검증(중복 확인)"까지만이다. MYP-040-01·06(비밀번호)과 MYP-040 닉네임 변경 명세가 이 입력에 없어서 현재 비밀번호 확인·로그인 회원 비밀번호 변경 API는 정의하지 않았다. 어느 그룹이 정의할지 정해야 한다. 근거: ACC-001-08, ACC-012-01·03, 기능 분배 3.1절 2·4번
10. **장소 검색이 백엔드를 거치는지와 PLC 적재 방식** — 기능 분배 3.1절 27번 비고에 "백엔드 경유 여부 미정"이라고 되어 있다. PLC에 KAKAO_PLC_ID가 있으니 카카오 결과를 PLC에 저장한다고 추정되지만, 즐겨찾기(PLC_BKMK.PLC_SN FK)는 저장된 PLC 행이 있어야 만들 수 있다. 검색 결과에 없는 업체를 즐겨찾기하는 경로, 자동완성 후보(입력 중 후보 표시)를 같은 `GET /places`로 할지 따로 둘지도 정해야 한다. 근거: HOS-001-03·09·23
11. **영업시간 컬럼이 없음, 좌표 타입** — 결과 카드·요약 카드에 영업시간을 표시하는데 PLC에 영업시간 컬럼이 없다(필드 표에서 뺐다). 위도·경도는 decimal이라 필드 표에 초안 작성 규칙의 타입 목록에 없는 `BigDecimal`을 썼다. 근거: HOS-001-07·25
12. **플레이스 명세의 "확인 필요" 항목** — 「전체」 탭의 검색 대상·즐겨찾기 범위, 검색 후보 선택 시 동작, 문장형 검색어(「다리수술잘하는곳」) 매칭, 추천순 기준·동점 순서, 0건·실패 안내, 즐겨찾기 실패 시 되돌림이 미정이다. 근거: HOS-001-01·03·04·06·09·23
13. **커뮤니티 지도 선택이 PLC 장소 검색으로 충분한지** — 목격 장소·돌봄 장소·채팅 주소 공유에는 일반 주소·좌표 검색이 필요하다. PLC는 반려 업체 데이터라 대상이 다르다. 기능 분배 3.1절 27번이 `place`로 정했으므로 `GET /places`로 분류했지만, 주소 검색 기능을 따로 둘지 정해야 한다. 근거: CMU-002-11, CMU-004-10, CMU-005-05
14. **지역(RGN) 목록 API를 정의하는 그룹이 없다** — 실종센터 지역 선택(전북), 펫돌봄 시·군·구 → 읍·면·동 연동 콤보박스에 RGN 목록이 필요한데 이 그룹 정의에도 `milestone.md` 담당 표 표에도 없다. 경로를 만들지 않았다. 근거: CMU-002-03, CMU-004-02
15. **첨부 이미지 업로드 방식 미정** — 게시글·실종·돌봄·채팅·돌봄 완료·1:1 문의 모두 사진을 받는다. 생성 요청에 multipart로 함께 보낼지, 공통 업로드 API(`global`)로 ATCH_FILE을 먼저 만들고 `atchFileSn` 목록을 보낼지 정해야 한다. 필드 표의 `atchFileSns`는 후자를 가정했다. 근거: CMU-001-14, CMU-002-10, CMU-004-09, CMU-005-05·08, CSC-003-09
16. **채팅 실시간 수신 방식** — 새 메시지 실시간 갱신, 배지 동기화는 REST만으로는 안 된다. WebSocket(STOMP)/SSE/폴링 중 무엇을 쓸지, COM-009 새 창과 본창 사이 동기화 방식도 정해야 한다. 근거: CMU-005-03·04
17. **매칭 거절·재협의·무응답 종료** — "거절·조건 재협의 시 확정하지 않는다"고만 있어 제공자 거절 동작, 조건 재제시(MTCH_CND_VER 새 버전) 경로가 없다. SYS_STNG.MTCH_NO_RSPNS_END_CRTR_DAY_CNT(매칭 무응답 종료)에 해당하는 명세도 없다. 다른 지원자 "모집 종료 안내"가 알림인지 채팅 메시지인지도 미정이다. 근거: CMU-005-06·07
18. **실종 제보 수정·삭제와 만료, 신고 누적 처리** — 실종 게시글 수정·삭제 기능이 명세에 없다. 30일 만료는 배치가 필요하지만 별도 기능 ID가 없다(기능 분배 3.1절 26번 비고). 신고 누적 5회를 명세는 "삭제 처리", SYS_STNG는 BLIND_DCLR_ACML_CNT(블라인드)로 적어 서로 다르다. 근거: CMU-002-09, CMU-001-13

20. **고객센터 명세 불일치** — 문의 유형을 "7종"이라고 하면서 실제로는 10개(건강기록·픽셀 캐릭터·플레이스·커뮤니티·포인트·결제·가계부·계정·로그인·기타)를 나열한다. 처리 상태를 한 곳은 「접수」, 다른 곳은 「미답변」이라 부른다. 근거: CSC-003-06·13

## DTO

DTO를 쓰면서 명세·테이블만으로 정하지 못한 것이다.

### 공통레이아웃·메인

1. **`expndLimSetYn` 이름이 규칙과 어긋남** — 컬럼이 아니라 `MBR.MM_EXPND_LIM_AMT` 존재 여부로 계산한 boolean인데 `_YN` 컬럼처럼 `Yn`을 붙였다. 초안 작성 규칙 1(계산 필드는 새로 짓되 `owner`·`canEdit`처럼)과 규칙 3(`Yn` 유지는 `_YN` 컬럼에만)에 따르면 `expndLimSet`이 맞다. 기존 초안 필드라 그대로 옮겼다. 근거: 이 초안, COM-008-10.
2. **위젯 저장 요청의 모양** — API 표의 요청 DTO가 `List<…>`가 아닌 `DashboardWidgetSaveRequest` 하나라서 `widgets: List<DashboardWidgetSaveItem>`을 감싼 객체로 두었다. 이 때문에 입력 목록에 없는 중첩 record `DashboardWidgetSaveItem`이 1개 생겼다. 본문을 JSON 배열(`List<DashboardWidgetSaveRequest>`)로 받을지, 감싼 객체로 받을지 정해야 한다. 근거: 이 초안, 초안 작성 규칙 9·11.
3. **위젯이 반려동물 단위인데 DTO에 `petSn`이 없음** — MAN-007은 "반려동물 단위로 저장", MAN-004는 탭 전환 시 위젯도 전환이라 하지만 MBR_DSHBD_WDGT에 PET_SN이 없어 요청·응답에 넣지 않았다(`issues.md` API의 공통레이아웃·메인 2번와 같은 원인). 테이블에 PET_SN을 추가하면 경로를 `/pets/{petSn}/…`로 옮기거나 필드를 추가해야 한다. 근거: MAN-004·007, DDL MBR_DSHBD_WDGT.
4. **위젯 저장 검증 규칙이 명세에 없음** — 명세에 있는 제약은 "표시 최대 5종"(MAN-006)뿐이다. 6종을 모두 보내야 하는지(PUT은 빠진 항목을 지운다), 코드 중복·`sortSeq` 중복을 400으로 막을지, 표시 5개 미만을 허용할지 없다. 근거: MAN-006·007, 규약 문서 A절 PUT 규약.
5. **공통코드명 필드 2개를 추가함** — 규칙 4에 따라 화면에 이름이 필요한 곳에 `dshbdWdgtCdNm`(위젯 카드 이름, MAN-006)과 `notiTypeCdNm`([유형] 라벨, COM-004-04)을 넣었다. 기존 초안에는 없는 필드다. 프론트가 코드값으로 이름을 매핑한다면 빼도 된다. MANG01·AIMG02 코드값 목록은 입력에 없다. 근거: 이 초안, COM-004-04, MAN-006.
6. **알림 설정 PUT과 요청에 없는 MBR 컬럼** — A절 PUT 규약은 "요청에 없는 항목은 지워진다"인데, 설정 값이 MBR 행의 컬럼이라 요청에 없는 `CHAR_CRT_NOTI_RCPTN_YN`(`issues.md` API의 공통레이아웃·메인 8번로 제외)·`MM_EXPND_LIM_AMT`를 서버가 건드리지 않아야 한다. 이 API에서는 "요청 필드만 갱신"으로 규약의 예외를 명시할지 정해야 한다. 근거: COM-008-12·14, 규약 문서 A절.
7. **알림 설정 응답의 `acntEml`이 평문** — 기존 초안은 복호화한 이메일을 그대로 준다(COM-008-03 "가입 이메일로 고정 표시"). 같은 이메일을 프로필 드롭다운은 마스킹해서 보여 준다(COM-005-02). 설정 화면에서 평문으로 보여 줄지, `maskedAcntEml`로 바꿀지 확인이 필요하다. 근거: 이 초안, COM-005-02, COM-008-03.
8. **`MemberSummaryResponse`의 필수 `Y` 2개를 확인해야 함** — `mbrNcnm`은 Y인데 MBR에 `NCNM_STNG_CMPTN_YN`(닉네임 설정 완료 여부)이 있어 닉네임이 비어 있는 회원이 있을 수 있다(추정). `maskedAcntEml`도 Y인데 소셜 가입(`JOIN_PATH_CD`)일 때 계정 이메일이 항상 있는지 DDL로 판정할 수 없다. 이메일 마스킹 규칙도 명세에 없다. 근거: 이 초안, DDL MBR.
9. **프로필 이미지를 `atchFileSn`만으로 줌** — 규칙 10에 따라 기존 초안의 `atchFileSn`을 따랐다. 공통레이아웃·메인 묶음에는 이 번호로 이미지를 받는 조회 API가 없어서, 화면이 어느 경로로 이미지를 받을지 다른 공통레이아웃·메인 묶음PI와 맞춰야 한다(`issues.md` API의 공통레이아웃·메인 20a번). 근거: 이 초안, COM-002-15.
10. **`GET /notifications` 쿼리 파라미터에 DTO가 없음** — `notiTypeCd`(List<String>)·`size`가 기존 초안에 있지만 입력 목록에 검색 조건 DTO(`NotificationSearchCond` 등)가 없어 쓰지 않았다. `@RequestParam`으로 받을지, `XxxSearchCond`(@Data)를 둘지 정해야 한다. 근거: 이 초안, in/dto-A.md.
11. **알림 행 안 처리에 필요한 식별자가 없음** — 공동양육 초대 [수락]·[거절](COM-004-08)에는 `jntBrupInvtnSn`, 펫돌봄 거래 알림(COM-004-09)에는 `otoChatRoomSn`이 필요하지만 INAPP_NOTI에 컬럼이 없어 `NotificationSummary`에 넣지 않았다. `mvmnPath` 문자열을 프론트가 해석할지, 컬럼·필드를 추가할지 정해야 한다(`issues.md` API의 공통레이아웃·메인 14·15번). 근거: COM-004-08·09.
12. **읽음 여부를 `prslDt`로만 표현함** — 기존 초안대로 `prslDt`(null이면 미읽음)를 그대로 옮겼다. 화면은 읽음 여부만 쓰고 읽은 시각을 표시한다는 명세는 없다(COM-004-06·11). 계산 필드 `read: Boolean`으로 바꿀지는 선택 사항이다. 근거: 이 초안.

### AI매니저·건강기록

이 초안 본문의 "(issues n)"은 이 파일의 번호다. `issues.md` API의 AI매니저·건강기록 n번은 API 목록 단계의 이슈다. 기존 초안에서 그대로 옮긴 근거 칸의 "issues 1"(`InspectionValueSummary.schdlDt`, `ReceiptCheckupCreateRequest.ckupYmd`)은 `issues.md` API의 AI매니저·건강기록 1번을 가리킨다.

1. **검사 수치 일괄 저장의 응답에 "제외된 항목"을 담을 자리가 없음.** 화면은 저장 뒤 "이미 등록된 항목입니다: WBC"를 안내해야 한다. 그런데 초안의 응답은 `List<InspectionValueResponse>`라서 저장된 행만 담긴다. 다음 둘 중 하나로 정해야 한다. (1) `{saved: List<InspectionValueResponse>, excludedArtclNms: List<String>}` 모양의 응답 DTO를 새로 둔다. (2) 화면이 저장 전에 GET으로 비교한다. 중복 기준(직접입력 항목을 이름으로 비교하는지)은 `issues.md` API의 AI매니저·건강기록 15번와 같이 정한다. 근거: HLT-007-03·04, HLT-005-02
2. **검진일 필드의 이름과 타입이 초안 안에서 서로 다름.** `InspectionValueSummary`는 검진일을 `schdlDt: LocalDateTime`으로 두었다. 영수증 요청은 `ckupYmd: LocalDate`로 두었다. 이번 초안은 검진 DTO 전부에 `ckupYmd`를 썼다. 화면은 날짜만 쓰므로 `InspectionValueSummary`도 `ckupYmd: LocalDate`로 바꾸자고 제안한다. 초안 필드라 고치지 않고 그대로 옮겼다. 근거: HLT-011-06·07, AIM-009-07
3. **검사 항목 기능 태그(혈구·신장·간·당)의 출처가 없음.** 혈액검사 행, 수치 추이 드롭다운, 입력 화면이 모두 태그를 표시한다. 그런데 태그를 담은 컬럼이 없다. `COM_CD`의 부모 코드(`COM_CD_PRNT_SN`)로 묶을지, 화면에 고정할지 정해야 한다. 정해지기 전이라 DTO에 태그 필드를 넣지 않았다. 한글 이름("크레아티닌")도 같은 문제다. 근거: HLT-005-02, HLT-007-02, HLT-011-06·07
4. **케어 완료 요청에 완료일이 없음.** 명세에서 완료는 타일 클릭(토글)뿐이고 날짜를 고르는 서술이 없다. 그래서 `CareCompletionCreateRequest`는 `careArtclSn` 하나만 받고 완료일은 서버의 오늘로 정한다고 보았다. 지난 날짜를 완료로 기록할 수 있는지 정해야 한다. 투약 항목의 `CMPTN_CYCL`이 그날 몇 번째 체크인지, 누적 회차인지도 정해야 한다. 근거: HLT-003-12
5. **자동 생성 케어 항목을 사용자가 수정할 수 있는지.** 명세는 "사용자가 추가한 항목만 직접 수정·삭제"라고 한다. 이 문장대로라면 처방약·반복 예방으로 생긴 항목(`prscSn`·`reptPrvntMngSn` 있음)은 수정할 수 없다. 반면 기본 정기관리 항목은 주기만 바꿀 수 있다고 따로 적혀 있다. 자동 생성 항목은 이 두 경우 어디에도 서술이 없다. `CareItemUpdateRequest`는 기본 항목 제약만 적었다. 근거: HLT-003-12, HLT-005-03·05
6. **검진 첨부 파일의 형식·용량 제약이 없음.** 관찰 사진과 영수증은 REQ-NFR-003(jpg·jpeg·png·webp, 10MB)을 따른다고 적혀 있다. 그런데 검진 첨부는 검사결과지 PDF를 받아야 하므로(PDF 분석) 이 규칙을 그대로 쓸 수 없다. 허용 확장자와 최대 크기를 정해야 한다(`SYS_STNG.FILE_MAX_SZ` 사용 여부 포함). 근거: HLT-005-01·04, HLT-011-09
7. **첨부 자료 카드의 "날짜"가 무엇인지.** 종합 건강기록의 첨부 카드는 "미리보기 → 파일명 → 날짜"를 보인다. 이 날짜가 업로드일인지 검진일인지 명세에 없다. 초안은 감사 컬럼 `CKUP_RCD_ATCH.REG_DT`를 `regDt`로 넣었다. 검진일이면 `ckupYmd`로 바꾼다. 근거: HLT-011-09
8. **관찰일의 타입.** `OBSRV_CYCL.OBSRV_DT`는 datetime이다. 하지만 화면은 날짜만 입력한다(기본값 오늘, 미래 불가). 규칙대로 `obsrvDt: LocalDateTime`으로 두었다. 이렇게 두면 시각을 00:00으로 채울지, 같은 날 여러 회차의 순서를 무엇으로 정할지 남는다. 컬럼을 date(`OBSRV_YMD`)로 바꾸는 안도 있다. 근거: HLT-002-32·17
9. **`ReceiptSectionResponse`의 모양은 기능 ID에서 지은 것임.** 구역명·반려동물 자동 연결·소계·할인·진료 품목·약품 행을 담았다. 컬럼 근거는 없다. 이 모양은 서버가 OCR 결과를 가공한다는 초안의 가정(`issues.md` API의 AI매니저·건강기록 4번)에 기대고 있다. 구역이 없는 영수증은 `sectionNm=null`인 구역 1개로 표현했다. 하단 할인은 서버가 비율로 배분해 구역의 `dscntAmt`에 넣는다고 보았다. 화면이 가공하기로 하면 이 DTO는 원문에 가까운 모양으로 다시 정한다. 근거: AIM-009-03·04·16·19·20·21, HLT-002-39·42
10. **PDF 분석 결과에서 혈액검사가 아닌 항목을 알리는 방법.** 명세는 그런 행을 저장 대상에서 빼고 안내하라고 한다. 초안은 서버가 그 행을 `items`에서 빼고 이름만 `excludedArtclNms`로 돌려준다고 두었다. 분석 엔진이 무엇을 돌려주는지 정해지지 않아(`issues.md` API의 AI매니저·건강기록 6번) 확정할 수 없다. 인식한 항목명을 HLTG12 코드로 바꾸는 주체도 정해야 한다. 근거: HLT-007-04·05
11. **병원명 최대 길이가 경로마다 다름.** 영수증 저장은 명세대로 50자다(AIM-009-26). 직접 입력·일정 등록은 명세에 길이가 없어 컬럼 길이 80자를 적었다. 같은 컬럼이 진입 경로에 따라 다르게 검증된다. `issues.md` API의 AI매니저·건강기록 17번과 함께 한 값으로 정해야 한다. 근거: AIM-009-26, HLT-002-28·45, HLT-003-35
12. **조합 필드 두 개의 이름.** (1) `CheckupSummary.schdlDelYn`: 근거는 `SCHDL.DEL_YN`이다. 규칙대로라면 이름이 `delYn`이어야 하지만 검진기록 자신의 삭제 여부로 읽힌다. 그래서 `schdl` 접두어를 붙였다. (2) `CareScheduleSummary.ckupRcdCnt`: 연결 검진기록 수로 [검진기록 없음]/[검진기록 있음] 뱃지와 가까운 예정 일정 후보를 가른다. 두 이름 모두 확인이 필요하다. 근거: HLT-002-05·46, HLT-003-31
13. **처방약 주기 체크(`careRfltYn`)의 기본값.** 명세는 주기 체크를 토글로만 서술하고 필수 여부와 기본값을 적지 않았다. 그래서 요청에서 `N`으로 두었다. 미전송 시 OFF로 저장할지 정해야 한다. 영수증 경로는 명세대로 서버가 OFF로 저장한다. 근거: HLT-005-03, AIM-009-11
14. **공유 API의 초안 DTO에 필드를 더함 — 화면 담당 합의 필요.** D절 12·14번 공유 기능의 응답에 다음을 "(추가)"로 넣었다. `CareItemSummary`·`CareItemResponse`에 `careCycleCdNm`과 `ckupRcdSn`([출처 보기]가 검진상세로 가려면 필요), `DailyHealthRecordSummary.crsdSttsCdNm`, `InspectionValueSummary.inspArtclCdNm`이다. `CheckupResponse`·`CareScheduleResponse`에도 필드를 더했다. 메인페이지(YAY)·AI매니저(LJS)가 같은 DTO를 쓰므로 함께 확인해야 한다. 공통코드명을 DTO마다 넣을지, 공통코드 조회 API로 화면이 바꿀지도 정해야 한다. 근거: 기능 분배 3.1절 12·14번, HLT-003-12, HLT-002-12·13, HLT-005-02

### 마이페이지

``issues.md` API의 마이페이지 항목 N번`은 API 목록 초안의 이 초안를 가리킨다.

1. **초대 대상 반려동물의 타입이 `List<PetSummary>`다.** 이 초안 GET /caregiver-invitations/{jntBrupInvtnSn}은 `pets`를 `List<PetSummary>`로 두고 `petSn`·`petNm`·`petSeCd` 3개만 적었다. 그런데 `PetSummary`는 GET /pets의 행 DTO라 필수 필드가 18개다(`brupRoleCd`·`rprsPetYn`·`caregiverCount` 포함). 초대를 받는 사람은 아직 양육관계가 없으므로 이 값을 채울 수 없다. 규칙 9에 따라 `CaregiverInvitationPetItem`으로 바꾸기를 제안한다. 초안 타입은 그대로 옮겼다. 근거: MYP-005-05, 초안 작성 규칙 9.
2. **decimal 정수 컬럼 타입이 둘로 갈린다.** 기존 초안은 `needPnt`(decimal(10,0))·`expndAmt`·`mmExpndLimAmt`(decimal(13,0))를 `Long`으로 두었다. 초안 작성 규칙 2는 decimal 정수를 `Integer`로 둔다. 컬럼 범위는 decimal(10,0)이 최대 9,999,999,999, decimal(13,0)이 최대 9,999,999,999,999이다. 둘 다 `Integer` 최대값 2,147,483,647을 넘는다. 이 초안은 금액 컬럼을 기존대로 `Long`, 새 포인트 필드(`hldPnt`·`dlngPnt`·`scorPnt`·`givePnt`)는 규칙대로 `Integer`로 두었다. 그래서 같은 포인트인데 `needPnt`는 `Long`, `hldPnt`는 `Integer`다. 하나로 정해야 한다.
3. **계산 boolean에 `Yn`이 붙어 있다.** 기존 초안의 `heldYn`(ItemSummary), `bdwgEditableYn`(PetResponse), `inqryRcptYn`(PixelCharacterResponse)은 컬럼이 아니라 계산 값이다. 규칙 1은 계산 boolean을 `owner`·`canEdit`처럼 짓고, 규칙 3의 `_YN` 유지는 컬럼에만 적용한다. `held`·`bdwgEditable`·`inqryRcpt`로 바꾸기를 제안한다. 이름은 그대로 옮겼다.
4. **PATCH로 숫자·일련번호 필드를 비울 방법이 없다.** A절은 `null`을 보내면 그대로 두고, 비울 때는 `""`을 보내라고 한다. 그런데 `Long`·`BigDecimal`에는 `""`을 쓸 수 없다. 이 문제가 걸리는 필드는 세 가지다. 지출을 공용으로 바꾸는 `ExpenseUpdateRequest.petSn`, 직접 입력 품종으로 바꿀 때의 `PetUpdateRequest.vrtySn`, 목표체중을 지우는 `PetUpdateRequest.goalBdwg`다. 해결 방법은 둘 중 하나다. 필드별로 해제 플래그를 두거나(프로필 사진은 `profilePhotoReset`으로 이렇게 했다), JSON Merge Patch처럼 `null`을 "비움"으로 읽도록 규약을 바꾼다. 근거: MYP-002-04, MYP-031-02, MYP-003-04, A절.
5. **회원정보 수정 요청이 multipart다.** 규칙 10에 따라 프로필 사진을 `MultipartFile profilePhoto`로 받았다. 그래서 `PATCH /members/me`가 `multipart/form-data`가 되고, 휴대전화도 폼 필드로 오게 된다. 이 방식과 `issues.md` API의 마이페이지 15번의 `atchFileSn` 방식(별도 업로드 API로 먼저 올리고 일련번호만 보냄) 중 무엇을 쓸지 정해야 한다. 프로필 사진의 형식·용량 규칙도 명세에 없다. 근거: MYP-040-02·08.
6. **`MemberResponse`는 가입 응답에도 쓸 수 있는 모양이다. 대신 두 가지를 확인해야 한다.** 이 DTO의 필드는 가입 직후에도 모두 값이 있다. 프로필 사진(`atchFileSn`)은 null이고, 이메일 가입이면 `snsAcntLinks`가 빈 목록이다. 첫째, 가입 직후 닉네임 모달·가입 완료 화면에 필요한 `ncnmStngCmptnYn`을 넣었다. 이 필드의 근거는 ACC-001-26·27이다. 둘째, 가입 직후는 서비스 미로그인 상태다(ACC-001-22). 이 상태에서 복호화한 이메일·휴대전화를 돌려줄지 로그인 담당(YAY)이 정해야 한다. 돌려주지 않는다면 가입·닉네임 설정에는 `mbrNcnm`·`ncnmStngCmptnYn`만 담은 응답을 따로 둔다. 근거: ACC-001-22·24·26·27, 로그인·플레이스·커뮤니티·고객센터 항목 4번.
7. **SNS 계정 표시 내용과 SNS 회원 이메일이 불분명하다.** MYP-040-09는 "연동된 SNS 계정 정보"를 표시한다고만 한다. 그래서 이 초안은 `snsOffrCd`(제공자)만 넣었다. `OFFR_ACNT_ID`는 제공자 내부 ID라 넣지 않았다. 또 SNS 회원 화면에는 이메일 항목이 없다. 그래도 가입 시 이메일 중복을 검사하므로(ACC-001-32) `acntEml`을 필수 `Y`로 두었다. SNS 제공자가 이메일을 주지 않는 경우가 있으면 `N`으로 바꿔야 한다.
8. **다중 삭제 요청의 `selectAll`은 이 초안이 지은 필드다.** "조회 결과 전체 선택"은 화면에 보이지 않는 건도 포함하므로 조건 삭제가 필요하다(MYP-030-18). 그래서 개별 선택(`expndSns`)과 조건 삭제를 구분하는 값이 필요해 이 필드를 지었다. 정해야 할 것이 셋 더 있다. 전체 선택한 뒤 일부를 해제할 수 있는지(그러면 제외 목록이 필요하다), 반려동물 필터의 "공용"을 어떤 값으로 표현할지(`issues.md` API의 마이페이지 9번), `DELETE` 요청에 본문을 쓸지(`issues.md` API의 마이페이지 12번)다. **[2026-10-22 결정]** `selectAll`을 없앴다. 조건 전체 삭제는 `POST /expenses/bulk-delete`가 맡는다(API 12번)
9. **연월 값의 타입 규약이 없다.** `ExpenseMonthSummary.yearMonth`와 쿼리 `yearMonth`(statistics·point-ledgers)는 연월만 담는다. A절은 `LocalDate`·`LocalDateTime` 형식만 정했다. 이 초안은 `String`(`yyyy-MM`)으로 두었다. `java.time.YearMonth`를 쓸지 공통 규약에 넣어야 한다.
10. **통계 응답의 구성은 이 초안이 정한 것이다.** 정한 내용은 넷이다. 공용 지출은 `pets`에 넣지 않고 `commonTotalExpndAmt`로 따로 준다. 날짜 항목의 반려동물·카테고리는 그날 1건일 때만 준다. `lastMonthTotalExpndAmt`는 "첫 달"이면 null이다. "첫 달"은 지출 기록이 시작된 달로 해석했다. 근거: MYP-030-01·02·05.
11. **`PixelCharacterResponse`의 필드는 두 응답의 합집합이다.** 이 초안에서 POST 응답은 `charCrtJobSn`을 갖고, GET 응답은 `bscCharSbstYn`·`inqryRcptYn`·`heldItems`를 갖는다. 같은 DTO라서 합쳤다. 그래서 GET에 `charCrtJobSn`(필수 `Y`)이 새로 생겼다. 또 중첩 record 이름 `HeldItemSummary`는 규칙 9의 `<부모>Item` 형식이 아니다. 같은 보유 아이템을 `HeldItemResponse`는 필드 3개, `HeldItemSummary`는 6개로 다르게 준다. 둘을 맞출지 정해야 한다.
12. **지출 행의 "(연동 해제)" 표기를 정할 수 없다.** "(삭제된 반려동물)"은 `PET.DEL_YN`으로 `ExpenseSummary.petDelYn`을 넣었다(MYP-002-07). 반면 "(연동 해제)"는 현재 회원과 그 반려동물의 `BRUP_REL.USE_YN`을 봐야 한다. 그런데 지출을 누구에게 보여 주는지(공유 범위)가 정해지지 않아 넣지 않았다(`issues.md` API의 마이페이지 10번, MYP-030-10).
13. **케어미션·포인트 내역의 표시값이 명세만으로 정해지지 않는다.** `DailyMissionSummary.givePnt`는 완료 전이나 자정 정산 전에 null인지 0인지 알 수 없어 `N`으로 두었다. `PointLedgerSummary`는 공통코드명(`pntDlngTypeCdNm`)으로 "검진기록 등록"을 표시하게 했다(MYP-020-08). 미션 적립이면 미션명(`DAY_MSN` → `CARE_MSN.MSN_NM`)을 보일지, `MEMO_CN`을 쓸지는 명세에 없다. **[2026-10-27 결정]** `givePnt`는 완료도 정산도 안 됐으면 null, 그 밖에는 값(0 포함)이다. 원장은 미션 하나에 1행(`DAY_MSN_SN` FK)이고, `PointLedgerSummary`에 `memoCn`(미션은 "{반려동물명} · {미션명}", 검진은 반려동물명, 아이템 구매는 구매 문구)과 `regDt`를 더했다. 내역의 내용은 `pntDlngTypeCdNm`과 `memoCn`으로 보인다
14. **초대 이메일의 검증 규칙이 없다.** MYP-005-01은 "이메일 주소를 직접 입력"이라고만 한다. `INVTN_TRGT_EML_ENC`는 text라 컬럼 길이로도 정할 수 없다. 형식 검사와 최대 길이는 회원가입 이메일 규칙(ACC)을 따를지 정해야 한다. 자기 자신이나 이미 연동된 회원을 초대할 때의 처리도 명세에 없다.

### 로그인·플레이스·커뮤니티·고객센터

1. **이미지 요청 방식이 초안 작성 규칙과 기존 초안 사이에서 갈린다**: 초안 작성 규칙 10은 파일 업로드를 `MultipartFile`로 받으라고 하는데, 기존 초안 `POST /inquiries`는 `atchFileSns: List<Long>`(업로드 API로 ATCH_FILE을 먼저 만든다)를 정했다. 같은 그룹 안에서 방식을 맞추려고 게시글·실종·돌봄 모집·돌봄 완료·채팅·문의의 요청을 모두 `atchFileSns`로 썼다. multipart로 바꾸면 이 필드들과 기존 초안을 함께 고쳐야 하고, 공통 업로드 API(`global`)도 정의해야 한다. 근거: 이 초안 `POST /inquiries`, 로그인·플레이스·커뮤니티·고객센터 항목 15, CMU-001-14, CMU-005-05, CSC-003-09
2. **PATCH에서 목록 필드의 의미가 없다**: api.md는 "보낸 필드만 바뀐다"만 정했다. `atchFileSns`·`pets`·`prtcShpCds`를 보내면 목록 전체를 바꾸는 것으로 적었다(빈 목록 `[]`이면 모두 삭제). 개별 추가·삭제 방식이 필요하면 바꿔야 한다. 근거: PostUpdateRequest, CareRecruitmentUpdateRequest, InquiryUpdateRequest, `docs/convention/api.md`
3. **PATCH의 "모든 필드 선택" 규칙이 맞지 않는 API가 있다**: `PATCH /members/me/nickname`은 기본 닉네임을 그대로 확정할 때도 설정 완료 여부를 Y로 바꿔야 하고(ACC-001-26), `PATCH /members/me/password`는 새 비밀번호와 확인값이 둘 다 있어야 의미가 있다. 규칙 8대로 필수 칸은 `N`으로 두었다. 둘을 예외(필수 Y)로 둘지, 상태 전이 POST로 바꿀지 정해야 한다. 근거: MemberNicknameUpdateRequest, PasswordChangeRequest, 초안 작성 규칙 8
4. **비밀번호 확인·변경 API는 근거 명세가 없다**: in/D.md에 MYP-040-01·06 본문이 없어 비밀번호 규칙은 가입·재설정 규칙(ACC-001-09, ACC-012-01·02)을 가져다 썼다. 아래를 정해야 한다. ① 확인 결과를 어떻게 이어 주는지(응답 토큰 / 서버 세션 / 변경 요청에 현재 비밀번호를 다시 넣기). ② `PasswordVerifyRequest`의 응답 DTO(목록에 없음). ③ 비밀번호가 없는 SNS 전용 회원이 회원정보 수정에 들어갈 때의 처리. ④ 변경 성공 시 다른 기기 로그인을 끝낼지(재설정은 끝낸다, ACC-012-03). 근거: MYP-040-01·06, 로그인·플레이스·커뮤니티·고객센터 항목 9
5. **토큰·멱등 식별값을 저장할 컬럼이 없다**: `signupTkn`(SNS 신규 가입 확인), `rcvryAuthrtTkn`(복구 확인 권한), `MemberCreateRequest`·`MemberRecoverRequest`의 `idmptDmndId`는 명세상 서버가 검증해야 하지만 DDL에 담을 곳이 없다. EML_CERT에는 비밀번호 재설정 토큰 해시만 있다. 로그인·플레이스·커뮤니티·고객센터 항목 3의 가입 진행 임시 상태 저장소와 함께 정해야 한다. 근거: ACC-001-14·31·32·43·45, ACC-002-09
6. **Refresh 토큰 전달 방식과 `TokenResponse` 근거**: `LoginResponse`·`SnsLoginResponse`에 `refreshToken`을 넣었지만, 기존 초안이 "전달 방식 쿠키/본문 미정"이라 쿠키로 정하면 빼야 한다. `POST /auth/refresh`는 요청 DTO가 `-`라서 쿠키를 전제한 것처럼 보이고, 명세 기능 ID도 없어 `TokenResponse.accessToken`의 근거를 로그인 기능(ACC-002-05)으로 대신 적었다. 재발급할 때 Refresh 토큰도 새로 줄지도 정해야 한다. 근거: 이 초안 `POST /auth/logout`·`POST /auth/refresh`, 로그인·플레이스·커뮤니티·고객센터 항목 1 **[2026-10-20 결정]** Access·Refresh 모두 httpOnly 쿠키다(`global/security/jwt/TokenCookies`, Refresh는 path `/api/auth`). `LoginResponse`·`SnsLoginResponse`에서 `accessToken`·`refreshToken`을 빼고 `TokenResponse`는 없앤다(YAY가 로그인을 만들 때 반영) **[2026-10-22 결정]** 토큰은 httpOnly 쿠키로만 오간다(`docs/convention/api.md`). `LoginResponse`·`SnsLoginResponse`에서 토큰 필드를 빼고 `TokenResponse`를 지웠다. `/auth/refresh` 응답은 `data` 없음
7. **보안코드 이미지 전달 형식**: `CaptchaResponse.captchaImg`를 Base64 문자열로 가정했다. 이미지 파일을 직접 돌려주는 API로 하면 `docs/convention/api.md`의 `ApiResponse` 예외(보호 파일 다운로드)에 넣어야 한다. 근거: ACC-002-18·19
8. **로그인 아이디 필드 이름이 API마다 다르다**: 기존 초안 `GET /auth/login-attempt-limits`의 쿼리는 `email`인데, 요청 DTO는 컬럼 규칙에 따라 `acntEml`(LoginRequest, CaptchaCreateRequest)과 `certTrgtEml`(EmailCertificationCreateRequest)로 지었다. 쿼리도 `acntEml`로 맞출지 정해야 한다. 근거: 이 초안 6행, 초안 작성 규칙 1, `docs/convention/api.md`(컬럼 값은 컬럼 이름)
9. **분기 결과값이 공통코드가 아니다**: `SnsLoginResponse.snsLoginRslt`, `EmailCertificationResponse.certRslt`, `ChatRoomResponse.myRole`은 명세의 분기를 담는 계산 필드인데 값 목록이 없다. 공통코드로 등록할지 Java enum으로 둘지, 값 이름을 정해야 한다. `certRslt`의 "미가입"을 정상 응답으로 줄지 404 오류로 줄지도 정해야 한다. 근거: ACC-002-09~11, ACC-001-06·43, ACC-011-08~10, CMU-005-11
10. **공지 작성자 표시와 본문 이미지**: 공지 상세는 "작성자(관리자)"를 표시한다(CSC-001-05). `NTC_MTTR.RGTR_ID`(등록자)가 있지만, 화면에 관리자 이름을 보일지 "관리자" 고정 문구로 둘지 명세에 없어 필드를 넣지 않았다. 이름을 보인다면 `RGTR_ID`가 무엇을 가리키는지(회원번호인지 관리자 계정인지)도 정해야 한다. 공지 본문의 이미지는 공지 첨부 테이블이 없어 본문 안에 넣는지 따로 두는지 정해야 한다. 근거: CSC-001-05
11. **돌봄 모집의 강아지 크기와 동의 컬럼**: 화면은 소형·중형·대형을 고르는데 테이블에는 체중(`RCRT_PET_KND.PET_BDWG`)만 있다. 체중 대표값(예: 소형 = 9.999)을 넣을지, 크기 공통코드 컬럼을 추가할지 정해야 한다. 목록 필터(크기)도 이 결정을 따른다. 또 "이용수칙 및 정보 공개 동의"를 컬럼 하나(`UTZTN_RUL_AGRE_YN`)로 받았다. 근거: CMU-004-02·06·11
12. **실종 제보 입력의 필수 여부와 날짜 타입**: 명세는 입력 항목만 나열하고 필수는 품종·동의만 밝혔다. 나열 항목(종류·이름·털색·목격 날짜·지역·좌표·전화번호·제목·내용)을 필수 Y, 특징·목격 장소명을 N으로 정한 것은 추정이다. "마지막 목격 날짜"는 날짜인데 컬럼은 `LAST_WTNS_DT` datetime이고, 목록 필터(오늘/1주일/1개월)도 이 값을 쓴다. 전화번호 형식 규칙도 없다. 근거: CMU-002-03·10·13
13. **매칭 요청 조건과 문의 수정 범위**: ① 매칭 요청 모달의 일정·돌봄 내용·비용을 모집 글에서 채운 값 그대로 보내는지, 보호자가 고칠 수 있는지 명세에 없다. 시급일 때 최저시급 검사를 매칭 조건에도 적용할지도 미정이다. ② 1:1 문의 수정은 "내용을 수정"이라고만 되어 있어 유형·제목·첨부까지 고칠 수 있는지 정해야 한다(초안은 모두 선택으로 열어 두었다). 근거: CMU-005-06, CMU-004-08, CSC-003-15
14. **삭제 댓글 표현**: "삭제된 댓글입니다" 대체를 서버가 문구로 내려줄지, `delYn`만 주고 화면이 표시할지 정해야 한다. 초안은 후자로, 삭제 댓글의 내용·작성자를 null로 했다. 근거: CMU-001-11, CMU-002-07
15. **장소 거리의 단위와 기존 초안에 더한 필드**: `PlaceSummary.distance`(기존 초안, Integer)의 단위(m 등)가 명세에 없다. 또 기존 초안 `GET /places`에 업체 유형 표시용 `plcClsfCdNm`(공통코드명)을 더했다. 기존 필드는 바꾸지 않았다. 근거: HOS-001-07·25, 초안 작성 규칙 4
